# Missing Features Build List and Brief Build Specs (Revised)

## Scope Changes
- Removed: the entire "Perchance generator" portion (generator module, prompt/template generator UI, generator-related ports, adapters, and tests).
- Renamed and repurposed: "Narrator" → "Agent". `NarratorOrchestrator` becomes `AgentOrchestrator`. The agent is a general-purpose task planner/executor, not a narrative generator.

## Priority 0 — Make the project compile and run

### 1. App-layer orchestration
**Build spec**
- Add `:app` Kotlin classes: `ChatViewModel`, `SettingsViewModel`, `ChatRepository`, `SettingsRepository`, and use cases such as `SendMessageUseCase`, `ApproveToolUseCase`, `LoadSettingsUseCase`.
- Wire Compose screens to ViewModels via `collectAsStateWithLifecycle`.
- Define UI state models: `ChatUiState`, `SettingsUiState`, `ToolApprovalUiState`.
- Remove any generator-related screens, routes, and navigation entries.
- Acceptance: `gradle assembleDebug` succeeds; app launches to `ChatScreen`; a user message updates UI state without crashing; no references to the removed generator remain.

### 2. Build and architectural guardrail verification
**Build spec**
- Ensure all modules (`:app`, `:security-interface`, `:core-engine`) have complete source sets and Gradle configs.
- Remove the generator module and any Gradle includes/dependencies pointing to it.
- Add CI checks: `gradle assembleDebug`, `gradle :core-engine:dependencies` must show zero third-party deps, and `grep` checks must fail on forbidden APIs in `:core-engine`.
- Add a guardrail check that fails if `perchance` or `generator` identifiers reappear in module names or source.
- Acceptance: clean build from fresh checkout; guardrail checks pass; no unresolved references; no orphaned generator artifacts.

## Priority 1 — Core security and orchestration

### 3. Security primitives implementation
**Build spec**
- Implement `AuditLogManager` with SHA-256 hash chain over tool invocations; append-only storage; tamper detection method.
- Implement `AndroidKeyStoreManager` using AES-256-GCM; API keys encrypted at rest; no plaintext secrets in logs or prefs.
- Implement `SecurityInterlock` enforcing L1/L2/L3 risk policies and approval flow.
- Add unit/integration tests for hash-chain integrity, tamper detection, and keystore encrypt/decrypt.
- Acceptance: tests prove audit log cannot be silently modified; secrets round-trip through keystore; interlock blocks unapproved L3 actions.

### 4. AgentOrchestrator and ProviderRegistry wiring
**Build spec**
- Implement `AgentOrchestrator` (renamed from `NarratorOrchestrator`) to accept user intent, plan tasks, call `AIGateway`, invoke tools through `ToolRegistry`, and return results.
- The agent is a general-purpose planner/executor: it decomposes user requests into steps, selects tools, and composes final responses.
- Implement `ProviderRegistry` to read settings and inject selected provider into the agent via `StateFlow`.
- Remove all generator-specific planning branches and prompts from the agent.
- Acceptance: agent can execute a simple plan (e.g., `http_get`) end-to-end in a test harness; no generator code paths remain.

## Priority 2 — Provider and tool functionality

### 5. AI provider adapters
**Build spec**
- Implement concrete `ChatModelPort` adapters for Gemini, OpenAI, Groq, and Ollama/local.
- Each adapter: request/response mapping, streaming if supported, error normalization, timeout handling.
- Remove any adapter code that only existed to serve the generator.
- Acceptance: adapter tests use mock HTTP servers; switching provider in settings changes active adapter; no generator-only adapter methods remain.

### 6. Tool executors and risk registry
**Build spec**
- Implement `ToolWorker` for `read_file`, `write_file`, `http_get`, `http_post`, `run_command`.
- Register each tool in `ToolRegistry` with risk level in `ToolRiskRegistry` (e.g., `http_get` = L2, `run_command` = L3).
- Add sandbox/path validation for file tools and command allowlist/denylist for `run_command`.
- Remove any generator-specific tools (e.g., template expanders, random-content tools) from the registry.
- Acceptance: each tool executes in isolation; risk levels trigger correct interlock behavior; registry contains no generator tools.

## Priority 3 — Product completeness

### 7. Settings persistence and injection
**Build spec**
- Implement DataStore or encrypted preferences for non-secret settings.
- Store API keys only via `AndroidKeyStoreManager`.
- Expose settings as `StateFlow` consumed by `ProviderRegistry` and `AgentOrchestrator`.
- Remove generator-related settings keys and migration paths.
- Acceptance: settings survive app restart; API keys never appear in plaintext storage; no generator settings remain in schema.

### 8. Chat UI state handling and error surfaces
**Build spec**
- Add loading, streaming, error, and tool-approval states to `ChatScreen`.
- Display audit/tool activity summaries and approval prompts for L3 actions.
- Show agent plan steps as they execute (agent-style trace view rather than narrative output).
- Remove generator UI elements, previews, and any "generate" affordances.
- Acceptance: user can send message, see streamed response, approve/deny tool call, and view error messages without crash; UI reflects agent plan/step trace.

### 9. End-to-end integration test harness
**Build spec**
- Create instrumented or Robolectric test that: sends chat message → agent plans → tool invoked → interlock approves/denies → audit record written → UI state updated.
- Use fake provider and fake tool worker for deterministic tests.
- Remove generator-specific test fixtures and golden files.
- Acceptance: test passes in CI and covers at least one L2 auto-approved tool and one L3 approval-required tool; no generator test artifacts remain.

### 10. Offline-first queue and sync (if in scope)
**Build spec**
- Implement local queue for pending tool actions/messages when offline.
- Define sync policy and conflict handling; ensure audit log remains append-only.
- Queue entries reference agent tasks (not generator jobs).
- Acceptance: actions queue offline and replay on reconnect; audit chain remains valid; queue schema has no generator fields.
